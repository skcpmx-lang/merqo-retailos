## 1. Objective
Implement P4.3 Backup & Restore as offline, atomic, consistent, verifiable, recoverable, auditable, Bengali-first system that allows owner to create valid backup, view history, restore safely with mandatory safety backup, verify integrity after restore, recover from corrupted backup, operate offline, preserve all financial/inventory/customer/supplier/audit data.

Goal is not `copy merqo.db` but **consistent backup → validation → safe storage → safe restore → integrity verification → recovery confirmation**.

## 2. Scope
In scope: Backup service, backup repository/metadata, backup creation, validation, history, restore workflow, restore safety, integrity verification, recovery checks, backup settings, backup/restore UI, backup-specific IPC, automated tests, regression, docs.

Out of scope (documented future): Cloud backup, Google Drive, OneDrive, Dropbox, SaaS backup, multi-store sync, cloud sync, ecommerce, V2 features, new accounting/inventory/POS workflow.

## 5. SQLite Consistency Strategy
Preferred order implemented in `createConsistentBackup`:
1. SQLite Online Backup API if available: `db.backup(filename)` returns Promise in better-sqlite3 v9 — verified via docs, not available in Linux sandbox but code tries first, logs.
2. `VACUUM INTO` — SQLite 3.27+ supports `VACUUM INTO 'path'` which creates consistent snapshot including WAL changes, works in both better-sqlite3 and node:sqlite fallback — tested via `node -e` with fallback connection, success, file 8192 bytes.
3. Safe checkpoint + controlled file copy: `PRAGMA wal_checkpoint(TRUNCATE)` then `fs.copyFileSync` — only if justified, documented as last resort.

Backup includes logical DB state represented by main DB + WAL changes + schema + all business data — VACUUM INTO and backup API include WAL, checkpoint ensures WAL flushed.

Do not silently omit WAL — handled.

Verified better-sqlite3 API existence via checking `typeof db.backup` — in sandbox better-sqlite3 bindings missing, so falls back to VACUUM INTO, which is safe and proven.

## 6. WAL Handling
- Backup: VACUUM INTO and backup API handle WAL internally, producing consistent file without needing to copy WAL/SHM separately. Checkpoint+copy does `wal_checkpoint(TRUNCATE)` to flush WAL into main DB before copy.
- Restore: Before restore, close DB via `closeConnection()` which closes WAL resources. Move current DB to recovery location, move WAL/SHM if exist to recovery files `recoveryPath-wal/shm`. After copying backup into live path, explicitly delete stale WAL/SHM from live path (`merqo.db-wal`, `merqo.db-shm`) to avoid inconsistent combination where old WAL attached to restored DB. After reopen, new WAL will be created fresh. Tested in `should handle stale WAL/SHM after restore` — creates dummy WAL/SHM, restore, verifies they are deleted.

## 7. Backup Format
V1: Validated SQLite backup file with metadata JSON sidecar.

- Backup DB: `MERQO-RetailOS-Backup-YYYY-MM-DD-HH-mm-ss-ms-shortId.db`
- Metadata: same path + `.json`, e.g., `...db.json`

- sourceDbPath
- notes

No secrets in metadata, no passwords/PINs plaintext.

Format documented, robust, filesystem-safe.

## 16. Restore Architecture
Deliberate design:

`Backup নির্বাচন` → `Validate` → `Show backup details` → `Confirm` (type RESTORE) → `Create current-data safety backup` → `Validate safety backup` → `Close DB` → `Replace/restore database safely` (move current to recovery, copy validated backup to live, delete stale WAL/SHM) → `Open DB` → `Run migrations if required` → `integrity_check` → `foreign_key_check` → business invariants → success → audit/log

If any step fails, attempt safe recovery using pre-restore safety backup.

Never leave app pointing at partially restored DB — uses recovery file and rollback.

Implemented in `BackupService.restoreBackup`.

## 17. Safety Backup
Mandatory before restore:

1. Validate selected backup
2. Warn user via UI dialog with details and warning Bengali
3. Create safety backup of current live DB via `createBackup({type: 'safety-pre-restore'})`
4. Validate safety backup via `validateBackup`
5. Only then proceed

If safety backup fails, DO NOT RESTORE, show Bengali error `বর্তমান ডেটার নিরাপত্তা ব্যাকআপ তৈরি করা যায়নি। তাই পুনরুদ্ধার বন্ধ করা হয়েছে।`

Tested in `should create safety backup before restore and require it` — verifies safety backup exists and type.

## 18. Failure Recovery
Tested scenarios:
- corrupt backup: create valid backup, corrupt copy by overwriting with zeros, attempt restore → validation fails, restore rejected, current DB remains intact — `should reject corrupted backup`
- incomplete backup: empty file `invalid.db` with text not sqlite → validation fails, restore rejected — `should reject invalid backup file`
- invalid SQLite file: same
- wrong schema: missing essential tables → validation fails
- incompatible migration state: newer backup with unknown migrations → rejected as `BACKUP_TOO_NEW`
- permission failure: handled via try/catch, Bengali error
- disk full: not testable safely, but code handles via try/catch and cleanup temp files, logs
- failure during copy: try/catch, rollback to safety backup
- failure reopening DB: catch, rollback

Expected: current DB remains recoverable, automatic rollback to safety backup, log detailed technical error, show Bengali user-safe error, never report restore success when failed.

Implemented rollback logic in `restoreBackup` catch block: close, delete failed live file + WAL/SHM, copy safety backup back or recovery file, reopen, validate rollback.

Tested in corruption tests and WAL handling.

## 19. Migration Compatibility
Restore may involve older MERQO version backup:

- Validate compatibility
- Restore (copy file)
- Apply pending migrations if safe via `Migrator.runMigrations()`
- Verify integrity

Never downgrade schema simply because old backup selected — we only run forward migrations, not downgrade.

If backup from newer incompatible version (has unknown migrations, version > current+5), reject restore with Bengali `এই ব্যাকআপটি বর্তমান MERQO RetailOS সংস্করণের চেয়ে নতুন।`

Tested via version check logic, though not fully with real newer DB.

## 23. IPC/Security
Backup files contain highly sensitive business data — do NOT upload, expose to renderer unnecessarily, place in public web dirs, expose arbitrary FS access, allow arbitrary restore paths without validation.

IPC must be:
- allowlisted: added 7 new channels to ALLOWED_IPC_CHANNELS
- typed: via `window.merqo.backup` typed methods
- Zod validated: `ipcPayloadSchemas` extended with backup channels, filePath min 1 max 500, type enum, businessId, notes max 500, retentionCount 1-100, etc
- permission checked: in handlers via sessionManager.getCurrentUser().permissions
- correlation-ID aware: via withErrorHandling Id.generate()

Renderer must not receive arbitrary Node FS APIs — only typed backup APIs, no raw fs.

File path validation via `isSafePath` prevents traversal, illegal Windows chars, and resolves within backupsDir.

## 33. Manual Recovery Procedure
For support/admin if application cannot start:

1. Locate userData:
   - Windows: `%APPDATA%\MERQO RetailOS\` — typically `C:\Users\<User>\AppData\Roaming\MERQO RetailOS\`
   - Contains `merqo.db`, `merqo.db-wal`, `merqo.db-shm`, `backups/`, `logs/`, `config.json`
   - Linux/mac dev: `app-data-test/` or `~/.config/MERQO RetailOS/`

2. Locate backups:
   - `userData/backups/` — files `MERQO-RetailOS-Backup-YYYY-MM-DD-HH-mm-ss-ms-*.db` + `.json` metadata
   - Identify latest valid backup via metadata JSON `validationStatus: valid`, `checksum`, `appVersion`, `createdAt`
   - Verify backup file size >0, not 0 bytes, checksum matches if possible via SHA-256

3. Preserve current database before recovery:
   - Copy `merqo.db` + `merqo.db-wal` + `merqo.db-shm` if exist to safe location e.g., Desktop `merqo-corrupted-backup/`
   - Do NOT delete current DB blindly
   - If app cannot launch, check `logs/` folder for error details

4. Restore through application (preferred):
   - Launch app, login as Owner, go to `ব্যাকআপ ও পুনরুদ্ধার`
   - Click `ফোল্ডার খুলুন` to verify backups exist
   - Select backup from list, click validate `যাচাই` — should show Integrity OK, FK OK
   - Click restore `পুনরুদ্ধার`, read warning `বর্তমান ডেটা প্রতিস্থাপিত হবে... নিরাপত্তা ব্যাকআপ তৈরি করা হবে`, type `RESTORE` to confirm
   - App will create safety backup, validate, close DB, replace, reopen, migrate, validate, show success `ডেটা সফলভাবে পুনরুদ্ধার করা হয়েছে।`
   - If restore fails, it attempts automatic rollback to safety backup, shows Bengali error, check logs

5. If application cannot launch at all:
   - Ensure no other MERQO process running
   - Backup current `merqo.db` as above
   - Delete `merqo.db-wal` and `merqo.db-shm` if exist (stale WAL)
   - Try launching again — if fails due to corrupted DB, replace `merqo.db` manually with latest valid backup file copy (copy backup DB file to `userData/merqo.db`), ensure WAL/SHM deleted, launch, check integrity via app's DB status or logs
   - Do NOT manually edit SQLite with arbitrary tools unless you understand schema and FKs
   - After manual replace, launch app, it will run migrations if needed, verify via `ব্যাকআপ ও পুনরুদ্ধার` validation

6. What to do if restore fails:
   - Check `logs/` for detailed error
   - Safety backup should exist in `backups/` as `safety-pre-restore` type — validate it
   - Attempt restore again from safety backup via UI
   - If still fails, contact support `merqoonline@gmail.com` with logs, backup file name, app version, Windows version, not with sensitive DB file unless secure channel

7. Do NOT:
   - Delete `backups/` folder blindly
   - Place backups inside installation directory or `.exe` directory
   - Upload backups to public cloud without encryption (V1 not encrypted, contains sensitive business data)
   - Manually edit `merqo.db` with text editor
   - Delete `merqo.db` before safety backup exists

This procedure is factual and safe.
